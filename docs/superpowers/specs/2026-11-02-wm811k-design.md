# WM-811K Portfolio Project: Semi-supervised vs Supervised Wafer Defect Classification + MLOps

## Context
Javian is applying for an AMD data science internship and wants a ~1-month portfolio project on the WM-811K wafer map dataset (found on Kaggle; no prior attachment to it). It should show depth in ML / data science / deep learning, plus strong preprocessing and MLOps. Modeling and MLOps are co-headlines (modeling slightly ahead); the full pipeline should read as one system, not a model with tooling bolted on. Semiconductor wafer defects are directly relevant to a chip company, which is the portfolio hook.

Resources: Colab A100, ~1 month, `LSWMD.pkl` (~2.1 GB) already in `amd-portfolio-project/` (untracked). Prior MLOps knowledge: experiment tracking, Docker, CI, drift monitoring.

## Goals
- A controlled comparison of supervised vs semi-supervised learning across label budgets (1%, 5%, 10%, 25%, 100% of labeled maps), reported as a label-efficiency curve.
- Three arms: (A) supervised: classical features + gradient boosting and a CNN from scratch; (B) self-supervised pretrain (SimCLR or MAE) on all ~811k maps, then fine-tune; (C) FixMatch-style consistency/pseudo-labeling on labeled + unlabeled.
- Rigorous preprocessing: handle ~78% unlabeled maps, severe class imbalance, variable map sizes, lot-aware splits to avoid leakage.
- A real MLOps layer: tracked experiments + model registry, containerized FastAPI inference, CI with meaningful tests, drift monitoring that triggers a response.
- A concise README that explains decisions and results.

## Non-goals / anti-goals
- Not a leaderboard chase; a single accuracy number is a failure signal. Report macro-F1 and per-class recall.
- No cloud deployment (Cloud Run etc.) and no Streamlit UI (user chose FastAPI only).
- Don't pad with extra model families beyond the three arms.
- Don't commit the 2.1 GB pickle to git.

## Decisions made by the user
- Modeling + MLOps are the main points; full pipeline second to modeling in emphasis.
- Compare semi-supervised and supervised approaches; use BOTH pretrain+fine-tune and FixMatch-style.
- Serving: FastAPI only.
- Colab A100 for training.

## My calls (flagged: please check)
- Stack: Python 3.11, Poetry, PyTorch, MLflow (tracking + registry), Hydra configs, DVC for data, Evidently for drift, GitHub Actions CI, multi-stage Docker. Reuses patterns from `mlops-assignment` (Hydra, Poetry Dockerfile, CI skeleton, DVC, MLflow).
- Drift demo: simulate a shift (e.g. a defect class's prevalence jumps or a new lot distribution) and show Evidently flagging it and the service emitting a retrain flag.
- Drift report served by FastAPI as an HTML endpoint (no separate dashboard).
- Multiple seeds per arm and label budget; same backbone across arms for a fair comparison.
- Because the label-budget sweep multiplies runs (3 arms x 5 budgets x seeds), keep the backbone small (ResNet-18-class on downscaled maps) and use mixed precision.

## Timeline (4 weeks)
1. **Week 1: data + scaffold.** Load/clean LSWMD, EDA, lot-aware stratified splits, resizing/encoding strategy, DVC + Hydra + MLflow wired in, CI skeleton with real preprocessing tests, supervised baselines (features + GBM, small CNN).
2. **Week 2: semi-supervised arms.** SimCLR/MAE pretraining on all maps in Colab, fine-tuning sweep; FixMatch-style arm; all runs logged to MLflow.
3. **Week 3: MLOps layer.** Register best models, FastAPI `/predict` + `/health` + `/drift-report`, Dockerize, extend CI (tests, lint, image build, model-quality gate), Evidently drift monitoring with simulated shift and retrain flag.
4. **Week 4: analysis + polish.** Label-efficiency curves, per-class error analysis, README with decisions/results/architecture diagram, short demo (GIF or notes), clean repo.

Risk: Weeks 2-3 are tight; if SimCLR/MAE pretraining runs long, cut label budgets to 3 points before cutting MLOps. Start MLOps scaffolding in week 1 so experiments run through it from the beginning.
